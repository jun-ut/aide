# ADR-0003: 何がコンテキストに蓄積するのか（ADR-0002 の訂正）と /clear 方針

- Status: accepted（**数値は [ADR-0004](0004-edit-payload-and-ast.md) で訂正**。
  重複排除キーと倍率計算のバグにより、tool_use のシェアを過小、実効単価を過大に見積もっていた。
  「thinking は蓄積せず最安」という結論の向きは変わらない）
- Date: 2026-09-03
- 訂正対象: [ADR-0002](0002-roadmap.md) の「コンテキストの 9 割は自分の出力」
- 前提: [ADR-0001](0001-context-economics.md)

## 訂正: 相関を構成と取り違えていた

ADR-0002 は `ctx ≈ 0.92 × 累積 output_tokens` という観測から
「コンテキストの中身の 9 割は Claude 自身の出力」と結論した。**これは誤り。**

`output_tokens` の大半は thinking であり、**thinking は後続のコンテキストに残らない**。
両者がターン数とともに増えるので相関しただけだった。

### thinking は transcript に保存されていない

```
keys: [ 'type', 'thinking', 'signature' ]
  thinking:  string len=0 ""            ← 本文は空
  signature: string len=1004 "CAIS6AUK…" ← 署名のみ
```

したがって thinking の量は直接測れない。残差で推定する:

```
thinking ≒ 累積 output_tokens − (可視テキスト + tool_use の入力)
```

## 測定（上位 5 セッション、message.id 単位で重複行を除去）

```
累積 output_tokens        1,894,723
  ├ thinking (残差・推定)  1,587,865  = output の 84%   ← 蓄積しない
  ├ 可視テキスト              27,505  = output の  1%   ← 蓄積する
  └ tool_use の入力          279,353  = output の 15%   ← 蓄積する
tool_result                1,351,517                    ← 蓄積する

コンテキストに蓄積するもの合計 1,658,375 tok
API リクエスト 2,623 回 / 平均 ctx 347,593 tok
```

### 加重コスト（生成時 + 蓄積、蓄積は 0.1x × 残リクエスト数）

```
種別              トークン      生成時        蓄積         合計   シェア  実効単価
tool_result      1,351,517   2,703,034  177,251,473  179,954,508  78.4%  133.2x
tool_use の入力    279,353   1,396,766   36,637,165   38,033,930  16.6%  136.2x
thinking         1,587,865   7,939,325            0    7,939,325   3.5%    5.0x
可視テキスト        27,505     137,524    3,607,262    3,744,786   1.6%  136.2x
```

**蓄積するトークン 1 個 ≒ thinking トークン 27 個。**

## 決定

1. **thinking: high を維持する。** output トークンの 84% を占めるが加重では 3.5%。
   完全に切っても節約は最大 3.5% で、代わりに性能を失う。割に合わない。
   → ADR-0002 の P0「出力の冗長さ」は**取り下げ**。可視テキストは加重の 1.6% しかなく、
     説明の簡潔さのために明快さを犠牲にする価値はない。
2. **本丸は tool_result（78.4%）。** ADR-0001 の元の見立てが正しかった。
   内訳（ADR-0002 のトークン基準測定）は Bash 44% / Read初回 26% / Read再読 12%。
   `agent` ラッパ・read-dedup・grep 優先はすべて正しい方向。
3. **新規: `tool_use` の入力（16.6%）に手を入れる。** 未着手かつ非自明。
   Edit の `old_string`/`new_string`、Write の全文、Bash のコマンド文字列。
   **生成時 5x に加えて蓄積もするので単価は tool_result より高い（136x）。**
   打ち手:
   - 大きなファイルを Write で丸ごと書き直さない。Edit で差分を当てる
   - Edit の `old_string` は一意になる最小範囲に留める
   - 同じファイルへの小さな Edit を何度も打つより、1 回にまとめる
4. **自動圧縮（auto-compact）は使わない。** 引き継ぎを `.agent/state.md` に残している以上、
   `/clear` で新規に始める方が素直。圧縮そのものの生成コストが無駄であり、
   圧縮結果が正確である保証もない。
   → `.agent/state.md` を書いてから 250k で `/clear` を既定の運用とする。
5. **実効単価 133x が示すもの**: 蓄積するトークンは、長いセッションでは自分のサイズの
   130 倍を課金される。これを断ち切れるのは `/clear` だけであり、
   だから clear の頻度が引き続き最大の打ち手である。

## 優先順位（確定版）

| # | 対象 | 加重シェア | 状態 |
|---|---|---|---|
| P0 | **`/clear` の頻度**（250k で切る） | 実効単価 133x を断ち切る唯一の手段 | 実装済（statusline / `agent age`） |
| P0 | **tool_result** — Bash 44% / Read初回 26% / Read再読 12% | 78.4% | 部分的（`agent` ラッパ・guard-bash・read-dedup） |
| P1 | **`tool_use` の入力**（Edit/Write の payload） | 16.6% | **未着手** |
| P1 | Bash の**呼び出し回数**（1,554 件、中央値 87 tok） | tool_result の 44% | 未着手（複合コマンド） |
| P1 | 初回 Read | tool_result の 26% | 未着手（`agent outline`） |
| P2 | 常駐ベースライン 22〜31k | 毎ターン 2〜3k 加重 | 未着手（skill 棚卸し） |
| — | ~~thinking~~ | 3.5% | **対象外**（性能とのトレードで負け） |
| — | ~~可視テキスト~~ | 1.6% | **対象外**（削っても効果なし） |

## Why not

- **thinking を下げない**: 加重 3.5%。性能とのトレードで明確に負け。
- **可視テキストを削らない**: 加重 1.6%。ここを削っても効果がなく、
  ユーザーへの説明が不親切になるだけ。
- **自動圧縮を併用しない**: 圧縮は「生成コストを払って蓄積を減らす」取引だが、
  引き継ぎファイルがあるなら `/clear` が同じ効果をゼロコストで得られる。

## 測定上の注意（同じ罠を二度踏まないために）

- **バイト数とトークン数を混同しない**（ADR-0002 で踏んだ）。
  transcript 内の画像は base64 で、トークン単価は `幅×高さ/750`。
- **相関を構成と取り違えない**（本 ADR で訂正した）。
  「A と B が一緒に増える」は「B の中身が A」を意味しない。
- **assistant メッセージは同じ内容が複数行に重複して出る。**
  必ず `message.id` 単位で重複排除してから数える。
- **thinking の本文は保存されていない。** 残差でしか推定できない。
  上の 84% は推定値であって実測値ではない。
