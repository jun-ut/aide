- Status: **一部 superseded by [ADR-0003](0003-what-actually-accumulates.md)**

- Date: 2026-09-02
- 前提: [ADR-0001](0001-context-economics.md)（加重コストの内訳。cacheRead 62% / cacheWrite 29% / output 9%）

## 訂正: 「Read 79%」は文字数の錯覚だった

ADR-0001 の tool_result 内訳は**文字数**ベースだった。transcript 内の画像は base64 で
格納されており、画像のトークン単価は `幅×高さ/750` で**バイト数と無関係**。
文字数で数えると画像を 20 倍程度過大評価する。

実際、45.5% が「画像の再読み込み」で、そのほぼ全部が 1 セッション（`4d8f3b77`、
スクリーンショットを 10 回読んでいた）に由来していた。

トークン基準で数え直した内訳（過去 8 セッション、テキスト 3.5ch/tok・画像 1,500tok/枚と仮定）:

```
推定 tool_result 合計 674,791 tok
  Bash                44.0%   296,841 tok  calls=1554
  Read テキスト(初)     25.7%   173,277 tok  calls= 169
  Edit/Write          12.6%    85,224 tok  calls=1872
  Read テキスト(再)     11.8%    79,714 tok  calls= 123
  画像(初+再)           3.8%    25,500 tok  calls=  17
```

**Bash が最大。** read-dedup hook が扱えるのは 11.8% であって 79% ではない。

> 教訓: バイト数とトークン数を混同しない。特に画像・base64・JSON が混ざる測定では
> 必ずモダリティごとに単価を変えて数える。

## ⚠ 以下の節は誤り（[ADR-0003](0003-what-actually-accumulates.md) で訂正）

`output_tokens` の 84% は thinking であり、thinking は後続コンテキストに蓄積しない。
`ctx` と `累積 output` が一緒に増えるのは、どちらもターン数に比例するからにすぎない。
**相関を構成と取り違えていた。** 実際に蓄積するのは tool_result 81% / tool_use の入力 17% /
可視テキスト 2% で、ADR-0001 の元の見立て（ツール出力が本丸）が正しかった。

## ~~より大きな発見: tool_result はコンテキストの 1 割しかない~~（誤り）

何がコンテキストを埋めているのかを分解した（`3eaddeac`、圧縮のない単調増加セッション）:

```
 進捗   ctx(実測)   累積output  累積tool_result  累積user
  25%    210,808     271,261        28,617          61
  50%    401,173     460,975        43,164          66
 100%    709,828     768,741        76,917         197
```

**ctx ≈ 0.92 × 累積 output。tool_result は output の約 1/10。**
コンテキストの中身は圧倒的に **Claude 自身の過去の出力**である。
（`ctx < 累積output` なのは thinking ブロックが後続ターンで落ちるため）

加重単価でも output が最悪:

```
output      : 生成時 5x + 以後 0.1x × 残ターン
tool_result : 生成時 2x + 以後 0.1x × 残ターン
```

**ボリュームでも単価でも output が最大。** 加重の 62% を占める cacheRead の中身は、
その大半が「自分の過去の発言を読み直している」分である。

## Bash は「大物」ではなく「長い尾」

```
Bash 1554 件 / 推定 296,841 tok  中央値 87 tok
  上位  1% ( 16件) が 11.4%
  上位 10% (156件) が 45.3%
  上位 20% (311件) が 63.3%
  最大の 1 件でも 3,626 tok

agent のラッパで吸収できる呼び出し: 194 件 / 32,476 tok (Bash の 10.9%)
```

巨大な事故は起きていない。ラッパの価値は総量削減ではなく**分散の抑制とテール保険**、
という ADR-0001 の見立て自体は支持された。ただし期待値は小さい。
**Bash の本丸は 1 件あたりの大きさではなく、呼び出し回数 1554 件の方。**

## その他の実測

- **常駐ベースライン（system + tools + skills + CLAUDE.md）: 22,159〜31,766 tok。**
  毎ターン 0.1x で 2〜3k 加重、clear / 失効のたびに 2x で書き直し。
  この中に、このプロジェクトと無関係な Cloudflare 系 skill が 13 個入っている。
- **圧縮イベントは 8 セッションで 2 件しか検出されなかった。** つまりほぼ圧縮せずに
  800k まで走り切っている。自動圧縮が 800k で発火すると 800k × 2x = 1.6M 加重を
  一撃で払うことになる。**意図的に 250k で clear すればこれを丸ごと回避できる。**

## 決定

1. **最大の未着手項目は「出力の冗長さ」。** これは hook では強制できない
   （PostToolUse は出力を差し替えられず、assistant の本文にも介入できない）。
   打ち手は `outputStyle` と AGENTS.md の記述、そして clear の頻度。
   → 次に取り組むのはこれ。
2. **read-dedup と agent ラッパは残す。** 期待値は下方修正されたが、
   コストはほぼゼロで、テール事故（画像 10 回読み、grep パイプの失敗）を確実に潰す。
3. **`agent stats` をトークン基準に直す。** 現状は文字数ベースで、同じ錯覚を再生産する。
   モダリティ別単価と「累積 output vs ctx」の分解を組み込む。
4. **250k での clear を最優先の習慣にする。** 自動圧縮の 1.6M 加重の一撃を回避できる。

## Why not

- **出力削減を hook でやろうとしない**: assistant の本文は hook の介入対象外。
  唯一効くのは設定（`outputStyle` / effortLevel）と、蓄積を消す clear。
- **Bash の呼び出し回数を hook で制限しない**: 中央値 87 tok の正常な呼び出しを
  邪魔するだけで、モデルが回避策（1 コマンドに詰め込む）を取ると可読性だけ落ちる。
  複合コマンド（`agent ctx` のような定型セット）を用意する方向で減らす。
- **画像を hook で自動縮小しない**: 実測では画像は 3.8% でしかなく、
  read-dedup が再読み込みを潰せば十分。縮小ツールへの依存を増やす価値がない。

## 未検証

- `agent test` のパーサ精度は合成出力でしか確認していない。実プロジェクトで要検証。
- read-dedup の誤検知率は未測定。自動圧縮でコンテキストから消えた内容を
  mtime だけでは見分けられない（PreCompact でクリアしているが検知漏れがあり得る）。
- 画像 1,500 tok/枚は仮定。実際の解像度から `幅×高さ/750` で数え直す余地がある。
