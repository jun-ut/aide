# ADR-0004: Edit/Write payload の内訳と、AST・symbol ベース手法をやらない判断

- Status: accepted
- Date: 2026-09-03
- 訂正対象: [ADR-0003](0003-what-actually-accumulates.md) の数値（結論の向きは変わらない）

## 訂正（3 度目）

ADR-0003 の「tool_use の入力 16.6%」「実効単価 133x」はどちらも誤り。原因は 2 つ:

1. **重複排除キーが誤り。** assistant メッセージは **1 ブロック 1 行**で jsonl に書かれる。
   `message.id` 単位で行ごと除外すると、同じメッセージの後続ブロックまで消える。
   正しくは `tool_use.id` / `tool_use_id` / テキストのハッシュで**ブロック単位**に除外する。
2. **蓄積倍率が誤り。** 「残りリクエスト数」に全セッションの合計を使っていたため、
   6 セッション分で約 5 倍に膨らんでいた。正しくは**セッション内の残りリクエスト数**。

## 確定版の加重内訳（6 セッション / 4,858 リクエスト / 平均 810 回/セッション）

```
種別                    トークン      生成時         蓄積         合計   シェア  実効単価
tool_result            1,444,945  2,889,891  41,171,014  44,060,905  49.1%   30.5x
tool_use: Write          276,832  1,384,160  15,292,626  16,676,786  18.6%   60.2x
tool_use: Edit           277,159  1,385,797  11,868,109  13,253,906  14.8%   47.8x
thinking (残差推定)     1,411,536  7,057,681           0   7,057,681   7.9%    5.0x
tool_use: Bash           111,491    557,453   4,488,129   5,045,582   5.6%   45.3x
可視テキスト              50,601    253,006   1,932,345   2,185,351   2.4%   43.2x
```

**Edit + Write = 33.4%**（ADR-0003 の 16.6% から倍増）。実効単価は 30〜60x。
thinking は 7.9%（同 3.5% から上方修正）だが、**5.0x のまま最安であり結論は変わらない**。

## Edit/Write の中身は圧縮できない

```
Edit  277,159 tok
  ├ old_string   66,090 (23.8%)  ← 既にコンテキストにある内容の再送。唯一の圧縮対象
  └ new_string  160,776 (58.0%)  ← 実際に書く新しいコード。圧縮不可能
  (残りは file_path / JSON の構造)
  replace_all の使用は 1,128 件中わずか 5 件

Write 276,832 tok
  ├ 新規ファイル 228,260 (82%)   ← 生成した新しいコード。圧縮不可能
  └ 既存の書き直し 20,967 (7.6%) ← Edit に置換可能
```

**symbol ベース編集で消せるのは old_string の 66,090 tok = 全体加重の約 3.5%。**
Write の書き直し置換を足しても 4% 台が上限。

## 「読みすぎ」は起きていない

```
同一セッションで Read も Edit もしたファイル 97 件
  読んだ合計 171,059 tok / 変更 payload 合計 257,306 tok → 比 0.66x
```

**読んだ量より書いた量の方が多い。** 「小さな変更のために巨大なファイルを読んでいる」
という前提は、少なくともこのリポジトリ群のデータでは成立しない。

ただしホットスポットは存在する:

```
x75 edits  src/cli/arena.ts     (read 21,407 / edit 4,150 = 5.2x)
x70 edits  docs/benchmark.md
x58 edits  src/bench/arena.ts
x50 edits  src/ui/Tracker.tsx
```

## 決定的な数字: 1 ターン = 34,759 加重トークン

平均 ctx 347,593 における 1 往復の追加コスト = `347,593 × 0.1 = 34,759`。
典型的な Read 1 回は約 1,000 tok で、蓄積込みでも `1,000 × 30 ≒ 30,000`。

> **symbol 単位の読み込みでファイル全体の読み込みを 1 回省いても、
> 「情報が足りないのでもう 1 回」が 1 度でも起きれば差し引きマイナス。**

これが AST / symbol ベース手法を評価する唯一の軸である。

## AST・symbol ベース手法の現状

| 実装 | 方式 |
|---|---|
| Aider の repo map | tree-sitter で定義抽出 → 参照グラフを PageRank → トークン予算に収まる地図 |
| Cline `list_code_definition_names` | tree-sitter でディレクトリ単位のトップレベル定義列挙 |
| Serena (MCP) | LSP ベースの `find_symbol` / `replace_symbol_body` / `insert_after_symbol` |
| Claude Code | AST ツールなし。ripgrep (`Grep`) + `Read(offset/limit)` |

**下火になった構造的理由:**

1. **プロンプトキャッシュが経済を変えた。** キャッシュ以前は毎ターン全トークンが定価で
   再課金されたのでコンテキスト最小化が至上命題だった。cache_read 0.1x で限界コストが
   1/10 になり、AST ナビゲーションの優位も同じ比率で縮んだ。
2. **言語ごとのセットアップ負債。** tree-sitter grammar と LSP サーバは言語ごとに
   導入・保守が要る。ripgrep はどこでも即動く。
3. **symbol は理解の単位ではない。** import・型・隣接コード・コメントが要る場面が多く、
   symbol だけ取ると往復が増える。そして往復は 34,759 加重トークン。

## 決定

1. **symbol ベース編集はやらない。** 上限 3.5%、Edit ツールは差し替え不可、
   Bash 経由の編集は差分が表示されず PostToolUse の lint も走らない
   （グローバル方針が禁じている）。費用対効果が合わない。
2. **`agent outline <file>` の優先度を下げる。** read:edit が 0.66x であり、
   読みすぎは起きていない。ADR-0002 で P1 に置いたのは前提が誤っていた。
3. **`agent map`（リポジトリの地図）は検討に値する。** Aider 方式の
   「定義の索引を 1 回だけ作ってキャッシュする」は、探索用の Bash
   （tool_result の 44%）を代替しうる。ただし往復を増やさないことが条件。
4. **設計改善（分割・純粋関数・クリーンアーキテクチャ）はトークンを理由に正当化しない。**
   保守性の理由でやるべきことであり、データはトークン面の効果を支持していない。
   効くとすれば「読む量が減る」経路ではなく「**試行回数が減る**」経路である。
5. **最大の打ち手は引き続き `/clear` の頻度。** 全コストは
   「ターン数 × コンテキストサイズ」に支配されており、これは payload の符号化ではなく
   タスク分割の帰結である。

## Why not

- **repo map を無条件に導入しない**: 地図自体がコンテキストを占め、
  しかも陳腐化する。作るなら「セッション開始時に 1 回、キャッシュ付き」に限る。
- **ファイル分割をトークン理由で推奨しない**: read:edit 0.66x が反証。
  ただし `arena.ts` (5.2x) のような個別のホットスポットは別途対応してよい。
- **`replace_all` を推奨しない**: 1,128 件中 5 件しか使われていないが、
  誤爆したときの被害が大きく、節約は誤差。

## 測定上の注意（4 つ目）

- **assistant メッセージは 1 ブロック 1 行で書かれる。**
  重複排除はメッセージ単位ではなく**ブロック単位のキー**で行う。
- **倍率計算はセッション境界を跨がせない。** 「残りリクエスト数」は必ずセッション内で数える。
