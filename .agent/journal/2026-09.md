## 2026-09-02 (続き) — 測定のやり直し

- guard-bash の誤爆 4 件目: heredoc の中身の正規表現 `/(test|vitest)/` の `|` を
  シェルのパイプと誤読。`stripHeredocs()` を追加。
  4 回踏んだので `test/guard-bash.test.mjs` (18 ケース) に固定した。
  → 教訓: シェル文字列の解析は「heredoc を落とす → 引用符を尊重して区切る →
     コマンド位置に錨を打つ」の 3 段が必須。1 段でも欠けると誤爆する。
- 自分の測定に誤りを発見。tool_result を**文字数**で数えていたため、base64 画像を
  20 倍過大評価していた。「Read 79%」は実質 1 セッションの画像再読み込みだった。
  トークン基準では Bash 44% / Read初回 26% / Read再読 12%。ADR-0002 に訂正を記録。
  → 教訓: バイト数とトークン数を混同しない。モダリティごとに単価を変えて数える。
- さらに分解して、より大きなことに気づいた: ctx ≈ 0.92 × 累積 output。
  tool_result はコンテキストのわずか 1 割。ツール出力の最適化は本丸ではなかった。
  本丸は「自分の過去の出力」であり、それを消せるのは clear だけ。
- Bash の集中度を測定: 中央値 87 tok、最大でも 3,626 tok、上位 10% で 45%。
  巨大事故はなく、agent ラッパが吸収できるのは Bash の 10.9% のみ。
  ラッパは総量削減ではなくテール保険として維持する。
- 常駐ベースラインは 22,159〜31,766 tok。無関係な Cloudflare skill が 13 個入っている。
- 圧縮イベントは 8 セッションで 2 件のみ。ほぼ圧縮せず 800k まで走っている。
  自動圧縮が 800k で発火すると 1.6M 加重の一撃になるので、250k clear で回避する。

## 2026-09-03 — 2度目の訂正 (thinking の扱い)

- ユーザーの指摘「出力の冗長さには thinking も含まれるのでは」から再測定。結果、
  **ADR-0002 の「コンテキストの 9 割は自分の出力」が誤りだった**と判明。
  `output_tokens` の 84% は thinking で、thinking は後続コンテキストに蓄積しない。
  ctx と累積 output が一緒に増えるのは、どちらもターン数に比例するからにすぎなかった。
  → 教訓: **相関を構成と取り違えない。**「A と B が一緒に増える」は
     「B の中身が A」を意味しない。分解して直接数えるまで結論を出さない。
- thinking の本文は transcript に保存されていない (空文字列 + signature 1004 ch のみ)。
  直接測れないので `output_tokens − 可視テキスト − tool_use入力` の残差で推定した。
  84% という数字は推定値であって実測値ではない、と ADR に明記した。
- 集計スクリプトを 2 回書き直した。1 回目はブロック単位の重複排除が壊れていて
  可視テキストを 1/5 に過小評価。**assistant メッセージは同じ内容が複数行に重複して
  出るので、message.id 単位で行ごと除外しないと正しく数えられない。**
- 確定した加重内訳: tool_result 78.4% / tool_use入力 16.6% / thinking 3.5% / 可視テキスト 1.6%。
  実効単価は蓄積するもの 133x に対し thinking 5.0x。蓄積 1 tok ≒ thinking 27 tok。
- 新しく見えた未着手項目: **tool_use の入力 (Edit/Write の payload) が 16.6%。**
  生成時 5x を払ったうえで蓄積もするので単価は tool_result より高い (136x)。
- AGENTS.md の「説明を書きすぎない」を撤回。可視テキストは加重 1.6% で、
  明快さを削っても得られるものがない。代わりに「Write より Edit」を追加。
- ユーザー方針: 自動圧縮は使わない。引き継ぎがあるなら /clear の方が素直で、
  圧縮の生成コストが無駄で、正確性も保証されない。ADR-0003 に決定として記録。

## 2026-09-03 — 3 度目の訂正 (集計バグ 2 件) と AST 手法の評価

- 「Edit の最適化は設計で是正できるか / AST・symbol ベース手法はどうなったか」を調査。
  その過程で ADR-0003 の数値に**バグ 2 件**を発見:
  1. **assistant メッセージは 1 ブロック 1 行で jsonl に書かれる。**
     `message.id` 単位で行ごと除外したため、同じメッセージの後続ブロックが全部消え、
     tool_use を 279k と過小評価していた (正しくは 688k)。
     → 重複排除は必ず**ブロック単位のキー** (`tool_use.id` / `tool_use_id` / 本文ハッシュ) で。
  2. **蓄積倍率で「残りリクエスト数」に全セッション合計を使っていた。**
     6 セッション分で約 5 倍に膨張し、実効単価 133x になっていた。正しくは 30〜60x。
     → 倍率計算はセッション境界を跨がせない。
- 確定値: tool_result 49.1% / Write 18.6% / Edit 14.8% / thinking 7.9% / Bash 5.6% / 可視テキスト 2.4%。
  Edit+Write は 33.4% で ADR-0003 の 16.6% から倍増したが、**中身が圧縮できない**:
  Edit の 58% は new_string (書くコードそのもの)、Write の 82% は新規ファイル。
  symbol ベース編集で消せるのは old_string の 3.5% だけ。
- **read:edit = 0.66x。** 読んだ量より書いた量が多く、「読みすぎ」は起きていない。
  → ファイル分割や `agent outline` をトークン理由で正当化できない。ADR-0002 の P1 は前提が誤り。
  例外は arena.ts (5.2x, 75 回編集) のようなホットスポットのみ。
- **決定的な数字: 1 往復 = 34,759 加重トークン** (平均 ctx 347k)。
  典型的な Read 1 回は蓄積込みでも約 30,000。
  → symbol 単位読み込みで Read を 1 回省いても、往復が 1 回増えたら差し引きマイナス。
     これが AST 手法を評価する唯一の軸であり、下火になった理由そのもの。
- AST 手法の現状を整理: Aider の repo map (tree-sitter + PageRank)、Cline の
  list_code_definition_names、Serena (LSP ベースの symbol 読み書き)。
  Claude Code は AST ツールを持たず ripgrep + Read(offset/limit) で通している。
  下火の理由は (1) プロンプトキャッシュが限界コストを 1/10 にした
  (2) 言語ごとの grammar/LSP 保守負債 (3) symbol は理解の単位ではなく往復が増える。
