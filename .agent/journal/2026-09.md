## 2026-09-03 — 3 度目の訂正 (集計バグ 2 件) と AST 手法の評価

- 「Edit の最適化は設計で是正できるか / AST・symbol ベース手法はどうなったか」を調査。
  その過程で ADR-0003 の数値に**バグ 2 件**を発見:
  1. **assistant メッセージは 1 ブロック 1 行で jsonl に書かれる。**
     `message.id` 単位で行ごと除外したため、同じメッセージの後続ブロックが全部消え、
     tool_use を 279k と過小評価していた (正しくは 688k)。
     → 重複排除は必ず**ブロック単位のキー** (`tool_use.id` / `tool_use_id` / 本文ハッシュ) で。
  2. **蓄積倍率で「残りリクエスト数」に全セッション合計を使っていた。**
     6 セッション分で約 5 倍に膨張し、実効単価 133x になっていた。正しくは 30〜60x。
     → 倍率計算はセッション境界を跨がせない。
- 確定値: tool_result 49.1% / Write 18.6% / Edit 14.8% / thinking 7.9% / Bash 5.6% / 可視テキスト 2.4%。
  Edit+Write は 33.4% で ADR-0003 の 16.6% から倍増したが、**中身が圧縮できない**:
  Edit の 58% は new_string (書くコードそのもの)、Write の 82% は新規ファイル。
  symbol ベース編集で消せるのは old_string の 3.5% だけ。
- **read:edit = 0.66x。** 読んだ量より書いた量が多く、「読みすぎ」は起きていない。
  → ファイル分割や `agent outline` をトークン理由で正当化できない。ADR-0002 の P1 は前提が誤り。
  例外は arena.ts (5.2x, 75 回編集) のようなホットスポットのみ。
- **決定的な数字: 1 往復 = 34,759 加重トークン** (平均 ctx 347k)。
  典型的な Read 1 回は蓄積込みでも約 30,000。
  → symbol 単位読み込みで Read を 1 回省いても、往復が 1 回増えたら差し引きマイナス。
     これが AST 手法を評価する唯一の軸であり、下火になった理由そのもの。
- AST 手法の現状を整理: Aider の repo map (tree-sitter + PageRank)、Cline の
  list_code_definition_names、Serena (LSP ベースの symbol 読み書き)。
  Claude Code は AST ツールを持たず ripgrep + Read(offset/limit) で通している。
  下火の理由は (1) プロンプトキャッシュが限界コストを 1/10 にした
  (2) 言語ごとの grammar/LSP 保守負債 (3) symbol は理解の単位ではなく往復が増える。

## 2026-09-07 — status_command の設計見直しと Windows 対応

### SessionStart で検証を走らせるのは間違いだった

sightline の `bin/status` が `agent test` / `agent lint` を同期実行していた。
一見よさそうに見えたが、壊れ方が悪い。`runStatus` の catch が `e.message` しか
返しておらず、**`execSync` がタイムアウト時に `e.stdout` に持っている途中出力を
捨てていた**。つまり冷えた `cargo test --workspace` が 30 秒を超えると、git も
ADR も TODO も地図も全部消えて 1 行のエラーに化ける。
**それが起きるのはビルドが冷えているとき = 新規 clone 直後**、地図が最も要る場面。

→ 3 点直した: (1) `agent last` を足して**走らせずに記録を鮮度つきで読む**
   (2) 途中出力を捨てない (3) 行数上限を掛ける。5.7s → 0.56s。

- 教訓 A: **SessionStart に載せる価値があるのは「作業中に変わらない事実」だけ。**
  HEAD・ADR・地図・TODO は載せていい。検証結果はその真逆で、開始時に計算しても
  最初の編集で嘘になる。「今」が要るならオンデマンドで叩けばいい。
- 教訓 B: **新鮮そうに見える古い数字より、古さが見えている数字。**
  `138 passed (12分前の記録)` の方が判断に使える。state.md の鮮度を HEAD との
  差で出しているのと同じ発想を、検証結果にも適用しただけ。
- 教訓 C: プレフィクスに入るものには上限を掛ける。他の出力経路は全部
  `limits.max_lines` に従うのに、**トークン単価が最も高い場所だけ無制限**で、
  コストが status_command の行儀に依存していた。
- なお token コストは問題ではなかった。22 行 ≒ 500 tok は 60 ターンで
  1 往復の約 5%。**効いていたのはレイテンシと壊れ方**。測る前に「重い＝トークン」と
  決めつけかけたが、実際の損失は別のところにあった。

### Windows: matcher が `Bash` だけだと Windows で穴が開く

`hooks/guard-bash.mjs` の PreToolUse matcher が `Bash` だけだった。
Claude Code のドキュメントに明示がある —「シェルコマンドを検査する hook は
`Bash|PowerShell` を matcher にせよ。Bash だけでは不十分」。
そして **Windows で Git Bash が無ければ PowerShell が唯一のシェル**になる。

つまり先日「CLAUDE.md に書いてあるだけで強制されていなかった」と言って
hook にした WRITE ルールが、**プラットフォームを変えるだけで再び
「書いてあるだけ」に戻る**状態だった。同じ失敗の 2 回目。

→ 教訓: **hook で強制した = 守られる、ではない。「どの入口から来ても通るか」まで
  見て初めて強制になる。** ツールが増えれば入口も増える。

その他 Windows で踏むはずだったもの:
- `spawnSync(cmd, {shell: true})` は Windows で **cmd.exe**。グロブを展開しないので
  `node --test test/*.test.mjs` (AIDE 自身のテスト) が動かない → `shellFor()` で
  Git Bash を明示。`CLAUDE_CODE_GIT_BASH_PATH` を再利用するのが一番ずれない。
- **`execSync` の `shell` は真偽値を受け付けない** (文字列か未指定のみ)。
  Linux では `shell: true` がたまたま動くので気づきにくい → `shellPath()` に分けた。
- `BOUNDED_PS` に `\b-First` と書いて動かなかった。**空白と `-` はどちらも
  非単語文字なので `\b` が境界にならない。** `(?:^|\s)-` に直した。
- 1 つの clone を WSL と Windows の両方から触るのは禁止と決めた。9p 越しに
  mtime がずれ、直前に入れた stop の催促 (mtime 比較) の前提が壊れる。

**Windows 実機では一度も動かしていない。** platform と existsSync を注入して
両方の枝は踏んだが、それはテストが通ることの証明であって動作の証明ではない。

## 2026-09-10 — sightline の実作業で出た 3 件を潰した

型推論の移植を 1 セッション回して、**往復を無駄にした場所**を数えた。3 件とも
「hook / 要約が設計どおり動いた結果として往復が増えた」形で、実測しないと出ない。

### 1. cargo の panic 本文が要約から丸ごと落ちていた (最大)

`block()` は空行で打ち切る。ところが Rust の panic 本文は**空行で始まることが多い**
(`assert!` の文言を `\n` で始めると必ずそうなる)。結果 `gist()` が拾えるのは
`thread ... panicked at FILE:LINE` の行だけになり、**要約が位置しか言わなくなる。**

sightline は「差分テストの最初の 1 件がそのまま次の作業指示」という進め方なので、
本文が落ちると要約の価値がゼロになる。**毎回 `agent log --grep` を打ち直していて、
1 セッションで 5 往復 (約 17 万加重トークン) を捨てていた。**

`cargoPanic()` を分けて、`panicked at` から位置を取り、その後ろを本文として最大
12 行返す。描画は**先頭の 1 件だけ**に本文を付ける (2 件目以降は 1 件目を直せば
変わるので、40 行を本文で埋める価値が無い)。
ついでに `error: test failed, to rerun pass ...` を失敗として数えるのをやめた ——
再実行の案内であって失敗ではないのに、1 本落ちるたびに見出しが 2 件に増えていた。

### 2. 「出力量が予測できない」は、測れなかったときの話だった

`cat <file>` を名前だけで止めていた。**止められた 2 回とも、同じ量を Read で
読み直して終わっている** —— 9〜30 行のファイル 7 個と、202 行のファイル 1 個。
guard が読む量を減らしていないなら、往復 1 回が丸損になる。

実在するリテラルなパスで合計 8KB 以下なら通す。**deny の理由が「予測できない」で
ある以上、測れたときに止めるのは筋が通らない。** 変数・グロブ・実在しないパスは
今までどおり止める (本当に測れないので)。

なお `cat f` は止まるのに `grep -v '^why:' f` は通る (BOUNDED に `grep` があるため)。
出力量は同じかそれ以上なので、**guard は名前による近似でしかない。** ここを締める
方向に直すと往復が増えるだけなので、緩い側に倒したまま残す。

### 3. state.md の 150 行 hook で 5 回連続で止まった

160 → 154 → 153 → 152 → 151 と刻んで削った。メッセージが「160 行で上限 150 行」
としか言わないので、**超過分を引き算して一度に削る**動きにならなかった。

「**あと N 行**削ってください」と、`##` の節ごとの行数の上位 3 つを出す。最後に
「刻んで削ると、そのたびにここで止まります」と失敗の形そのものを書いた。

### sightline 側にも 1 件

`agent lint` が Sightline の正準形 (`slc fmt --check examples`) を見ていなかった。
`bin/status` だけが見ていたので**緑の定義が 2 つあり**、手で叩く羽目になっていた。
lint に入れて 1 つにした (sightline の `.agent/config.yml`)。
